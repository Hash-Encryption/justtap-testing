# JUSTTAP V2 AGENT CONTRACT

This contract is authoritative for all coding agents working in this repository.

## Required reading

Before changing architecture or implementing a phase, read:

1. `AGENTS.md`
2. `docs/ARCHITECTURE.md`
3. `docs/DECISIONS.md`
4. `docs/STATUS.md`
5. the relevant phase in `docs/V2-PLAN.md` and any phase-specific document

Read `docs/INVENTORY.md` and `docs/SECURITY.md` before touching a duplicated or security-sensitive subsystem.

## Architecture rules

- TanStack Start under `src/` is the only target framework and router.
- `app/`, root `components/`, and root `lib/` are frozen legacy Next.js code. Do not add new functionality there.
- Do not introduce another routing system.
- Do not introduce static customer-card generation or `generateStaticParams()` for cards.
- Do not create `c.html`, `/c/* -> /c.html`, query-string, or browser-path slug fallbacks.
- Do not add demo-card slugs, Pro Demo Mode, fake card fallbacks, or any other demo-card special case.
- Do not parse a slug again in browser code when the router already resolved it.
- Do not duplicate a feature to “fix” an existing feature. Understand the implementation and migrate deliberately.
- Do not edit `src/routeTree.gen.ts` manually; it is generated by TanStack Router.
- Never hard-code credentials or API secrets.
- Never expose server-only secrets through `VITE_*` or `NEXT_PUBLIC_*` variables.
- Never allow the client to control billing entitlement, `plan_tier`, subscription state, or Pro authorization.
- Never bypass Supabase RLS as a shortcut. Public and private card fields require explicit access boundaries.
- Future database changes use versioned migrations; do not treat one mutable schema file as migration history.

## Git and validation rules

- Preserve Lovable Git history. Never force push, rebase, amend, or squash published Lovable history.
- Never reset away or discard user changes.
- Do not push or deploy without explicit user authorization.
- Run validation appropriate to the modified application; the legacy Next build is not proof that V2 works.
- Inspect the diff for generated files, secrets, and unintended legacy changes before handoff.
- Update `docs/STATUS.md`, `docs/INVENTORY.md`, and affected ADRs when architecture or phase state changes.

## Phase checkpoint rule

1. Implement and validate only the current phase.
2. Produce the completion report, then stop for architecture review.
3. Do not commit the phase until the user explicitly approves it.
4. After approval, create one clean checkpoint commit for that phase.
5. Do not begin the next phase until the prior phase checkpoint commit exists.

Never combine two phases in one commit, and never begin a phase with uncommitted changes from the previous phase.
